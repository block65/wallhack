## Pontoon MCP — Findings

### Tool Completeness
Sufficient for VM lifecycle and basic inspection. `vm_exec`, `vm_port_probe`, `topology_get`, `network_tcpdump` cover the essentials. Missing: a topology visualization or summary tool — parsing the full JSON topology is painful for a 27-VM range.

### UX & Discoverability
- Tool names are mostly clear. `vm_inject` vs `vm_cp` is confusing — both copy files into a VM via 9p. The distinction isn't obvious without reading descriptions carefully.
- `vm_logs` (host-side console) vs `vm_tail` (bg command logs) — makes sense but the naming doesn't signal the difference. Something like `vm_console` vs `vm_tail` would be clearer.

### Error Messages & Feedback
- `vm_exec` returning empty output with no error is common and hard to distinguish from "command ran but produced no output" vs "command failed silently". The `echo "exit=$?"` workaround is needed too often.

### Specific Issues
| Severity     | Finding                                                                       | Suggested Fix                                                                                  |
| ------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 🟡 Minor      | `vm_inject` vs `vm_cp` — two tools for the same operation, unclear difference | Consolidate into one tool or clarify naming                                                    |
| 🟡 Minor      | `vm_logs` only shows kernel console, not daemon stdout/stderr                 | Capture service stdout/stderr to a log file in init, or document this limitation               |
| 🟡 Minor      | `vm_exec` empty output indistinguishable from silent failure                  | Return exit code alongside output, or at minimum document that empty = success                 |
| 🟢 Suggestion | `topology_get` returns raw JSON — no visual summary                           | Add a `topology_summary` tool that returns a text diagram or condensed network map             |
| 🟢 Suggestion | `vm_port_probe` bypasses TUN — uses VM's native TCP stack                     | Document this clearly, or add a note that it tests direct connectivity not tunnel connectivity |

## Wallhack MCP — Findings

### Tool Completeness
The MCP exposes enough for basic pivoting: connect, route, peers, info. Missing:
- No way to see what the exit node can reach (no diagnostic "can this peer route to X?" tool)
- No relay setup through MCP — multi-hop pivoting requires wallhack nodes pre-deployed on intermediate hosts
- `ping` with a peer name is advertised in the description but returns "not yet implemented"

### Logging Quality
N/A — no log output visible through the MCP. The daemon runs inside VMs and its logs aren't surfaced. `vm_logs` only shows kernel console.

### Terminology Consistency
Good after the recent rename pass. `info`, `peers`, `routes`, `hint_set`, `route_del` — all follow noun-verb consistently. One exception: `disconnect` (verb only, no noun prefix) breaks the pattern vs `peer_disconnect` internally.

### UX & Workflow
- **First-hop pivoting works cleanly.** `info` → `peers` → `routes` → test connectivity. The auto-route feature is excellent — gateway-perimeter's advertised routes appeared automatically.
- **`hint_set` / `hint_set_auto` are opaque.** No documentation via the MCP about what hints do or when to use them. A CTF player would ignore these entirely.
- **Stats show zero despite real traffic.** After fetching a page through the tunnel, `stats` still reported 0 bytes in/out. Either stats aren't wired to the data path or there's a bug.
- **Latency permanently shows `—`.** Both peers show no latency measurement despite 14+ minutes of uptime and heartbeat pings. Likely a regression from the latency channel refactor — the server-side accept path may not be updating the registry.

### Error Messages
- Invalid CIDR: "invalid CIDR: not-a-cidr" — excellent, clear and specific.
- Nonexistent peer: "peer not found: nonexistent-peer" — good.
- Peer ping: "peer ping not yet implemented" — honest but the tool description shouldn't advertise this capability.
- Silent route failure: adding a route to a CIDR the exit node can't reach succeeds with "OK" but traffic goes nowhere. No feedback that the route is unroutable.

## Cross-Cutting Observations

1. **Pontoon + Wallhack MCP together are usable** for single-hop pivoting. The workflow (check topology → check peers → verify routes → probe targets) is logical and discoverable.

2. **Multi-hop is the gap.** The range has 4 hops to the target but wallhack can only reach 1 hop deep. This is a known limitation (relay bidi stream bridging not yet implemented per project notes), but it means UAT can't test the full range depth.

3. **Observability gap.** Neither MCP surfaces daemon logs. When something doesn't work (latency missing, stats zero, peer disconnected), there's no way to diagnose through the MCPs alone. A `logs` or `debug` tool on the wallhack MCP would help.

4. **`vm_port_probe` vs tunnel connectivity** is a trap. `port_probe` tests direct VM-to-VM connectivity, not tunnel connectivity. I used it first and thought the tunnel was broken. `nc` through the TUN worked fine. This distinction needs documentation or a separate `tunnel_probe` tool.
