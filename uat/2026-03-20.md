## Pontoon MCP — Findings

### Tool Completeness
Sufficient for basic range lifecycle and VM inspection. `range_up`, `range_down`, `vm_exec`, `vm_ps`, `vm_logs`, `vm_exec_bg`, `vm_tail`, `vm_inject`/`vm_cp`, `vm_pkill`, `network_tcpdump` — all present and mostly functional. Missing: no topology enumeration tool (no way to list VMs or networks from the MCP; must read `pontoon.yml` manually).

### UX & Discoverability
Tool names are logical and consistent. The `vm_exec` / `vm_exec_bg` / `vm_tail` pattern is well-designed. `vm_ps` returning structured JSON is excellent — far more usable than raw `ps aux` output from `vm_exec`. One pain point: `range_up` output lists PIDs but no names — "launched (pid=3758486)" is meaningless to a user who hasn't memorised the launch order.

### Error Messages & Feedback
`deny_root` enforcement on `loot` VM returns a clear error: "error: root exec denied on loot" — good. No silent failures observed.

### Specific Issues

| Severity | Finding | Suggested Fix |
|----------|---------|---------------|
| 🟡 Minor | `range_up` progress output shows `[vm] launched (pid=…)` with no VM name — user can't tell which VMs are ready or in what order | Include VM name: `[vm/attacker] launched (pid=3758486)` |
| 🟡 Minor | `vm_logs` shows only raw kernel serial output — wallhack application logs don't appear there, making VM-side wallhack debugging completely opaque | Capture wallhack stdout/stderr to a tagged log accessible via `vm_tail` |
| 🟡 Minor | `vm_exec` `ps aux \| grep wallhack` as root returned only the grep process; `vm_ps` correctly showed wallhack running (pid 45). Output inconsistency between the two tools | Likely a timing/pipe artifact — document or investigate |
| 🟢 Suggestion | No topology listing tool — user must parse `pontoon.yml` to understand network structure | Add `range_info` or `topology_get` tool returning network CIDRs and VM names/IPs |

## Wallhack MCP — Findings

### Tool Completeness
The MCP exposes 14 tools but **two of the most fundamental are non-functional stubs**: `connect` and `listen` both return "not yet implemented — specify at startup". `disconnect` is partially implemented: disconnecting a named peer works, but `disconnect` with no peer (transport-level disconnect) also returns "not yet implemented". This means:

- Cannot add new peer connections at runtime
- Cannot open new listeners at runtime
- Cannot perform the reverse-target connection scenario (exit at 10.99.5.50:9000 waiting for entry to connect)
- Cannot reach `udp-only` VM (which needs a `:53` listener that can't be opened dynamically)

### Logging Quality
Log content is good — appropriate verbosity at info level, clean format. The "No authentication configured" warning is a nice security nudge. Log ring buffer via `logs` tool is useful. One issue: wallhack logs are not surfaced in `vm_logs` (kernel serial console) on the VM side, making it impossible to debug VM-side wallhack issues without a separate log capture mechanism.

### Terminology Consistency
**Bug**: "Role resolved" log lines are misleading. The log shows:
```
Role resolved: name=gateway-perimeter addr=10.99.1.10:45548 role=entry
```
…but the `peers` tool shows `gateway-perimeter role=exit`. The log is displaying *this node's* resolved role ("entry") next to the peer's name, making it read as if gateway-perimeter's role is "entry". This contradicts the `peers` output. Should instead be:
```
Role resolved: my_role=entry peer=gateway-perimeter peer_role=exit
```

### UX & Workflow
**What works well:**
- `info` output is clean and complete: name, role, listen addr, capabilities, version with build metadata, uptime. First thing I checked; answered all basic questions immediately.
- Auto-routing is excellent: `10.99.2.0/24 via gateway-perimeter (auto)` — routes appear automatically when a peer connects, labelled with `(auto)` to distinguish from manual routes.
- `route_add` warning is **excellent**: "peer gateway-perimeter does not advertise a route covering 10.99.3.0/24; traffic may not reach the destination" — tells the user exactly why the route won't work, preventing dead-end chasing.
- `peers` output is informative: name, address, role, status, latency, capabilities all on one line.
- Disconnect log attribution "Peer disconnected: web-filter (via API)" is a nice auditability touch.

**What's missing/broken:**
- `listen` and `connect` are stubs — the entire dynamic peer management workflow is blocked.
- `hint_set` / `hint_set_auto` return only "OK" — no feedback about the current hint state or effect. After calling `hint_set role=entry level=fixed`, I had no confirmation the daemon changed behaviour.
- `stats` shows 0 connections and 0 flows even after traffic successfully passed through the tunnel (ping and HTTP confirmed). Stats don't reflect actual traffic.
- After forcibly disconnecting `web-filter`, the exit peer **never reconnected** (checked ~90s later). A CTF player would expect auto-reconnect with backoff.
- Reaching deeper networks (datacenter, management, vault) requires relay chaining, which is not possible through the MCP. This is the primary blocker to completing the range objective.

### Error Messages
Good signal-to-noise. `listen` and `connect` error messages identify the problem ("dynamic … not yet implemented") but give no workaround. A CTF player hitting these errors has no forward path surfaced by the error itself.

### Specific Issues

| Severity | Finding | Suggested Fix |
|----------|---------|---------------|
| 🔴 Critical | `connect` MCP tool is a stub — "dynamic connect not yet implemented". Blocks reverse-target scenario and any manual peer addition at runtime | Implement dynamic connect, or clearly mark the tool as not yet available in its description |
| 🔴 Critical | `listen` MCP tool is a stub — "dynamic listen not yet implemented". Blocks `udp-only` VM (needs `:53`) and any runtime listener changes | Same — implement or document clearly in tool description |
| 🔴 Critical | Multi-hop relay chaining not achievable via MCP — no way to reach datacenter/management/vault from the attacker | Expose relay configuration via MCP, or document the `vm_exec` workaround for chaining wallhack instances |
| 🟡 Minor | `disconnect` with no peer returns "not yet implemented" — but named peer disconnect works | Implement transport disconnect or return a meaningful error explaining the distinction |
| 🟡 Minor | "Role resolved: name=\<peer\> role=entry" log is misleading — displays attacker's resolved role next to peer's name, contradicting `peers` output | Fix log format to clearly separate my_role and peer_role |
| 🟡 Minor | `stats` shows 0 connections/flows even after confirmed traffic flows through tunnel | Fix stats tracking to count TUN flows and connections |
| 🟡 Minor | `hint_set` / `hint_set_auto` return "OK" with no state reflection | Return current hint state in the response, e.g. "role hint set: entry=fixed" |
| 🟡 Minor | Exit peer (web-filter) did not auto-reconnect after being forcibly disconnected by the entry | Implement reconnect backoff on exit peers, or document expected behaviour clearly |
| 🟢 Suggestion | `wallhack --help` has no examples — a CTF player from Ligolo-ng muscle memory would benefit from a one-liner showing the connect/listen/relay workflow | Add examples section to help output |
| 🟢 Suggestion | `info` output shows `capabilities: tun=true listen=true connect=false` — `connect=false` on the entry node is counterintuitive (it's the one initiating connections) | Clarify capabilities semantics in docs or rename to reflect actual meaning |

## Cross-Cutting Observations

- **Pontoon and Wallhack complement each other well for the first hop.** `range_up` → auto-peer-connect → auto-routes is a smooth first experience. Reaching the office network required zero manual configuration on the attacker side. This is the best part of the current experience.
- **The range topology is well-constructed** — realistic with gateways, masquerading, and deny rules. `deny_cp` and `deny_root` enforcement is solid. The loot → credentials → deeper chain is exactly how a real CTF progression works.
- **The MCP's effective coverage ends at the office network.** Everything past 10.99.2.0/24 requires capabilities (dynamic connect/listen, relay config) that don't yet exist in the MCP. If a CTF player is expected to reach gold, the relay workflow must be MCP-accessible.
- **Log visibility gap**: Pontoon can only see kernel serial output via `vm_logs`; Wallhack MCP can only see the attacker daemon's ring buffer via `logs`. There is no MCP path to view VM-side wallhack logs for peer nodes. This is a debugging gap that will frustrate both players and developers.
